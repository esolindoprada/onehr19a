This Guardrail is mandatory for design, implementation, runtime remediation, upgrade, migration
and acceptance of `onehr_mobile_kiosk`. It is not advisory.

## PROJECT IDENTITY PREFLIGHT — HARD GATE 0

Before any source change verify all seven:

- PROJECT: OneHR NEW
- ADDON: `onehr_mobile_kiosk`
- AUTHORITATIVE BASELINE: Architecture v2 + Registry v1 + OneHR 25 Addons Specification +
  current accepted sibling contracts + latest user workspace
- PRESERVATION RULE: exactly the product-approved kiosk ownership and current Attendance/Time Off boundaries
- ALLOWED CHANGE: enterprise replacement of the tutorial scaffold; Odoo 19 hardening; UI/security/tests
- FORBIDDEN CHANGE: ownership/dependency drift, duplicate canonical facts, security weakening, feature deletion
- CURRENT VERIFIED STATUS: source, runtime and enterprise-completeness statuses reported separately

Any ambiguity blocks implementation.

## HARD GATE 1 — CODEX BUKAN ARCHITECT

Codex may only implement an already-approved contract or repair one proven source defect. It may
not decide model ownership, dependency direction, security boundary, workflow, data retention,
biometric policy, public API ownership or enterprise scope.

## HARD GATE 2 — EXISTING FUNCTION PRESERVATION

Mandatory preservation targets include QR/NFC, check-in/out, optional geotag/geofence, kiosk mode,
face-ready capability, today's schedule, leave balance, quick Time Off, device token, online/offline
queue/sync, device usage/error reporting, multi-company isolation, audit and soft external API hook.

No target may be removed merely because a test or install becomes easier.

## HARD GATE 3 — ENTERPRISE COMPLETENESS BUKAN SEKADAR TEST PASS

Syntax, XML parse, install, upgrade or 24/24 tests do not prove enterprise completion. Final
acceptance also requires browser/device UAT, token/security negative tests, offline/reconnect,
geofence, cross-company, report/analytics, cross-addon regression and exact Registry-row review.

## HARD GATE 4 — FULL STRUCTURAL INVENTORY

Before implementation/repair inventory models, fields, lifecycle, controllers, groups, ACLs,
record rules, data/cron, views/actions/menus, templates/assets, reports, tests and integration
contracts. `FULL_STRUCTURAL_INVENTORY.md` is the source inventory.

Approved persistent kiosk models are exactly:

1. `onehr.kiosk.device`
2. `onehr.kiosk.log`

No third persistent queue model or duplicate attendance model may be created without Registry approval.

## HARD GATE 5 — HUMAN-FRIENDLY CODING STRUCTURE

Business responsibilities are split into readable modules:

- `device.py` — device policy, token, kiosk-facing services
- `log.py` — immutable event evidence and retry lifecycle
- `attendance_bridge.py` — narrow canonical attendance bridge
- `security_helpers.py` — explicit server authority
- `action_helpers.py` — reusable UI actions
- `controllers/kiosk.py` — authenticated HTTP/JSON-RPC boundary
- dedicated XML by model/purpose
- JS/CSS dedicated to kiosk UX.

No monolithic generated `models.py` scaffold is accepted.

## HARD GATE 6 — PROFESSIONAL FORM DESIGN

Operational forms must present identity/context first, status in header, decision actions near the
record, metrics as smart buttons, configuration in coherent notebook pages and historical evidence
read-only. UI may not expose secret plaintext or invite unsafe direct state editing.

## HARD GATE 7 — UI/UX MATRIX PER MODEL

`UI_UX_MATRIX.md` must cover both persistent models and the kiosk surface. Statusbar, smart button,
body action and One2many row action are used only where they serve an operational decision.

## HARD GATE 8 — SEARCH VIEW WAJIB

Every persistent business model must have an explicit Search view. Generic autogenerated search is
not accepted.

## HARD GATE 9 — LIST VIEW ENTERPRISE QUALITY

Lists must expose decision data, lifecycle/state, operational exception information and useful row
actions. Name-only CRUD lists fail this gate.

## HARD GATE 10 — SECURITY TIDAK BOLEH DIKALAHKAN UI

Hiding a button is never authorization. ACL, global company rules, assigned-device rules and model
methods enforce authority independently of the UI.

Additional mandatory kiosk security:

- authenticated user + device token
- raw token not persisted
- no raw QR/NFC credential in server log evidence
- no biometric material
- no business `.sudo()`
- quick Time Off uses employee user authority
- retry target work uses configured service user authority.

## HARD GATE 11 — INTENTIONALLY UNDEFINED

The user-defined OneHR gate sequence does not assign a meaning to Gate 11. This implementation
does **not** invent one. Any future Gate 11 meaning requires explicit architecture/user approval.

## HARD GATE 12 — CODE STYLE HUMAN FRIENDLY

Prefer named constants, short domain helpers, meaningful method names, explicit validation and
normal Odoo idioms. Avoid opaque metaprogramming, compressed generated code and gratuitous
abstraction. A developer must be able to safely edit the addon manually.

## HARD GATE 13 — COMMENTS YANG BERGUNA

Comments explain *why* a security, ownership, privacy or integration boundary exists. Comments that
only restate obvious syntax are avoided.

## HARD GATE 14 — CODEX RETRY LIMIT

If Codex is explicitly assigned a runtime repair:

- maximum attempts per task: **2**
- same root cause may be repeated: **1** time maximum
- classify the failure before changing source
- accepted failure classes:
  - environment/harness
  - Odoo compatibility
  - addon source defect
  - test defect
  - data/migration
  - architecture/registry conflict
- environment/harness failure must not trigger source mutation
- architecture/registry conflict requires STOP and escalation
- do not delete/skip tests, reduce security, drop features or change dependency/ownership to obtain PASS.

Every repair must preserve a root-cause note and exact changed files.

## HARD GATE 15 — ENTERPRISE COMPLETENESS MATRIX

`ENTERPRISE_COMPLETENESS_MATRIX.md` is mandatory evidence. Final status cannot be FINAL/FROZEN or
MOVE_FORWARD_READY while any applicable runtime/security/registry/upgrade/regression gate is pending.

## Runtime stop markers

Stop implementation/repair immediately when:

- the failing artifact is not identified,
- a proposed repair changes model ownership or hard dependency,
- a fix requires a public unauthenticated attendance bypass,
- a fix requires storing plaintext device/employee secrets,
- security must be weakened,
- the same Codex root cause has already repeated once,
- the second Codex attempt fails,
- exact Registry authority conflicts with this build.

## Acceptance vocabulary

- `SOURCE_ACCEPTANCE: PASS` — source structure/static checks only.
- `WINDOWS_RUNTIME_ACCEPTANCE: PASS` — target Odoo runtime scenarios passed.
- `SOURCE_ENTERPRISE_COMPLETENESS: PASS_FOR_RUNTIME` — source may proceed to runtime; not final.
- `ONEHR_MOBILE_KIOSK_MOVE_FORWARD_READY: YES` — only after every applicable hard gate passes.
